## 是什么

开发者 Maurice Heumann 在博客中记录了一个为期 3 个月的项目：用 AI 代理反编译一款流行的第一人称射击游戏，目标是得到准确、稳定、功能完整的 C++ 重建版本，而不仅是概念验证。项目由 RektInator、Future、st0rm 等社区成员共同参与。

技术栈方面，团队同时使用 Claude Max（20x）和 Codex Pro 订阅，模型以 Sonnet 5 为主，也大量使用 Opus 5.5、Luna、Sol 和 Terra。代理分别运行在 Claude Code CLI 和 Codex CLI 中，其他代理框架“选择几乎不重要”。进度用 GitHub Issues 跟踪（每个 .cpp 文件一个 issue），代理之间通过 Discord 频道通信，CI 失败由 GitHub webhook 推送到该频道。反汇编与反编译使用 Hex-Rays 官方 ida-mcp，作者评价其“非常稳定、无头、支持项目所需的一切”。

第一个月有 4 个代理：3 个 worker 负责反编译和提交，1 个 reviewer 被动协调并审查提交。团队把默认 90% 的上下文压缩阈值降到 42%，以减少“已反编译函数”这类易失信息占用上下文；还发现代理会随时间失焦、未完成当前函数就跳到下一个、在 CI 失败通知已到 Discord 的情况下仍空转、甚至未彻底检查就关闭 issue。为此他们写了目标与行为规范文档，并用每小时 cron 任务提醒代理重读。

## 为什么重要

项目表面进展顺利：第一个月就反编译了约 80% 的游戏，游戏能启动、主菜单可见、地图可加载。但作者指出，代码虽然“极其可读”，语义却是错的——代理使用了错误的函数签名、类型或结构体布局，凭空发明逻辑，或删掉自认为不必要的逻辑。代理还引入了不必要的架构改动，例如把游戏通过全局变量访问的配置变量改成哈希表查找，开销高出几个数量级。

作者认为 reviewer 代理只能抓 bug，无法质疑架构决策。这揭示了当前多代理自主工作流的核心短板：可读性和表面进度会掩盖语义正确性的缺失，而缺乏人类实时干预时，代理的“漂移”很难被自动发现。

HN 讨论则聚焦成本与商业可持续性。有评论估算，按 2026 年 API 价格，5000 亿 token 大约花费 10 万至 75 万美元，旗舰模型输入价格多在每百万 token 150 至 400 美元区间。有人指出这类工作大多跑在高度补贴的订阅计划上，怀疑 Anthropic 乐于以 4000 美元卖出价值 10 万美元的算力，以推高增长数据并向投资者证明补贴停止后需求仍在。反对者以 Uber 早期补贴后盈利为例，认为用户会认识到价值并接受更高价格；也有人举 Moviepass 作为补贴失败的例子，并质疑“不亏钱”的说法。

## 发给 AI 的落地指令

```text
你是一名资深软件工程师，请评估以下多代理反编译工作流的风险并给出改进方案。

背景：
- 目标：将一款老游戏准确反编译为可编译、可读的 C++，要求语义正确、行为一致。
- 配置：Claude Max 与 Codex Pro 订阅并用，模型以 Sonnet 5 为主，代理跑在 Claude Code CLI / Codex CLI。
- 协作：GitHub Issues 跟踪进度（每个 .cpp 一个 issue），Discord 频道供代理互聊与人类介入，CI 失败经 webhook 推送。
- 反汇编：Hex-Rays ida-mcp。
- 已知问题：上下文压缩阈值从 90% 降到 42%；代理会失焦、跳函数、空转、误关 issue；reviewer 只能抓 bug，无法质疑架构；产出代码可读但语义错误（错误签名/类型/结构体布局、发明或删除逻辑、把全局变量访问改成哈希表）。

请输出：
1. 针对“语义正确性”的验证机制设计，要求可自动化、能发现错误签名与结构体布局偏差。
2. 针对“架构漂移”的审查流程，说明如何让 reviewer 或人类在合并前拦截不必要的重构。
3. 针对“代理失焦”的上下文与任务管理策略，包括压缩阈值、任务粒度、心跳与重读规范的具体做法。
4. 一套可量化的项目健康指标，用于区分“表面进度”与“真实正确率”。
5. 成本估算框架：给定 token 消耗与模型单价，如何判断继续补贴式订阅是否值得。

约束：只基于上述背景推理，不要假设未提供的游戏名称或代码细节；若信息不足，明确指出需要补充什么。
```
